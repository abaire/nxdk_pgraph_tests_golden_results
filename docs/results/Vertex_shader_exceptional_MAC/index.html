Vertex_shader_exceptional_MAC

Description
Renders MUL, ADD, MAD, MIN, MAX, SLT, SGE, DP3, DPH, DP4 and DST results on exceptional inputs (+-0, +-inf, NaN encodings, denormals and FLT_MAX). Expected values were measured bit-exactly on hardware by reading results back from constant registers (the "VSH Exceptional" tests in nxdk_low_level_nv2a_tests). The "Vertex shader exceptional" suites route the same computations to visible outputs so that the GPU shader translation used by emulators is exercised.
Each test uses one shader that computes the op into r10, then compares all four lanes of r10 with the expected bits in c[100]: lane i of SGE(r, e) * SGE(e, r) is 1 exactly when the bits of lane i match under the hardware's sign-magnitude ordering. A DP4 with a one-hot constant picks the lane of the record. Only those exact 0 or 1 values pass through the DP4, which would otherwise flush -0, denormals and NaN payloads.
Each test renders one row per result component, labeled on the left. The cells in each row are:
hw: green if the result has the same bits as the hardware result, otherwise red.
rf: the expected value compared with itself. Always green on hardware. An emulator that compares IEEE style draws this red when the expected value is a NaN, meaning that its hw cell cannot judge the row.
hw: green if the result has the same bits as the hardware result, otherwise red.
rf: the expected value compared with itself. Always green on hardware. An emulator that compares IEEE style draws this red when the expected value is a NaN, meaning that its hw cell cannot judge the row.
The bottom row draws raw SGE results (green = 1): SGE(NaN, NaN), SGE(-0, +0) and SGE(+0, denormal). Hardware gives 1, 0, 0. An IEEE comparison gives 0, 1, 0 and one that also treats denormals as zero gives 0, 1, 1.
Hardware values are verified for constant register readback. The rendered output still has to be confirmed on hardware.
